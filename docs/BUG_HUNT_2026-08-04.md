## Critical / High

### 1. `decrypt` / `encrypt` / `optimize` delete the original file on Ctrl-C before any replacement is written (data loss)

- **Files:** `PdfTool/pdftooldecrypt.cpp:98-102`, `PdfTool/pdftoolencrypt.cpp:107-110`, `PdfTool/pdftooloptimize.cpp:104-107`
- **Defect:** All three commands write in place (`options.document` is both input and output). Each has a cancellation check *before* `writer.write(...)` runs:
  ```cpp
  if (isCancelRequested())
  {
      removePartialOutput(options.document);   // deletes the ORIGINAL, still-untouched file
      return ExitFailure;
  }
  pdf::PDFOperationResult result = writer.write(options.document, &document, true);
  ```
  `writer.write(..., true)` uses `QSaveFile`, so the real file on disk is never touched until the write commits — nothing "partial" exists yet at the point `removePartialOutput` runs. `removePartialOutput()` (`pdftoolabstractapplication.cpp:1665-1681`) unconditionally does `QFile::remove(outputPath)`.
- **Failure scenario:** Run `pdftool decrypt secret.pdf`, send SIGINT/Ctrl-C in the window between `builder.build()` and `writer.write()` starting (`pdftooldecrypt.cpp:96-105` — an arbitrarily wide window on a large document). The user's only copy of `secret.pdf` is deleted and nothing replaces it. Same pattern applies to `encrypt` and `optimize`.
- **Note:** `pdftoolredact.cpp:106-113` has the same shape but writes to a separate `options.redactedDocument` path, so it does not destroy the source document — only a would-be output file (lower severity, expected `--force` overwrite semantics apply).

### 2. OCR sidecar crashes and permanently stops processing on a non-object JSON request

- **File:** `frisket-ocr/service/main.py:33-40`
- **Defect:**
  ```python
  try:
      response = run_ocr(request)
  except Exception as exc:
      response = {
          "page": request.get("page", 0),   # request may not be a dict here
          ...
      }
  ```
  If `request` parses as valid JSON but isn't an object (e.g. `42`, `null`, `[1, 2]`), `run_ocr()` raises `AttributeError`. The handler then calls `request.get(...)` on that same non-dict value, raising a second, unhandled `AttributeError` that escapes the `except` block entirely and kills the `for line in sys.stdin` loop — the persistent sidecar process dies.
- **Failure scenario:** Any malformed request line (not necessarily malicious — a serialization bug upstream that emits a list/scalar instead of an object for one page) permanently disables OCR for the rest of the run. On the C++ side, `PdfTool/pdftoolocr.cpp` (`OcrSidecarClient::sendRequest`, ~lines 213-262) then times out waiting 120s per remaining page instead of getting a clean error.

### 3. `PDFBleedFixup::apply` mutates page box metadata even when `analyzeOnly` ("dry run") is requested

- **File:** `Pdf4QtLibCore/sources/pdfbleedfixup.cpp:647-672` (box writes), confirmed unconditional relative to `settings.analyzeOnly` — the box-rewrite calls are gated only on `settings.expandMediaBox/expandCropBox/expandBleedBox/expandTrimBox/reanchorOrigin`, never on `analyzeOnly`
- **Defect:** The comment at line 598 ("A dry run reports box geometry only, so it must not pay [raster] cost") only covers rasterization (line 599: `needsRaster = !sidesToApply.empty() && !settings.analyzeOnly`). But `builder->setPageMediaBox/CropBox/BleedBox/TrimBox` (lines 649-667) and the final `*document = *modifier.getDocument()` commit run regardless of `analyzeOnly`. `analyzeOnly=true` only skips painting bleed artwork — it still rewrites box metadata on the in-memory document.
- **Failure scenario:** The current CLI (`pdftooladdbleed.cpp`) is safe today only because it discards its local `document` after a `--dry-run` call and never persists it. Any other/future caller (e.g. a GUI "preview" reusing the live working document instead of a throwaway copy) would have its page boxes silently rewritten by a call that is supposed to be side-effect-free.

### 4. Preflight report schema has drifted from what the engine actually emits

- **Files:** `Pdf4QtLibCore/sources/preflightengine.h:42` (`PREFLIGHT_REPORT_SCHEMA_VERSION = 3`) vs. `frisket-preflight/schemas/report.schema.json:10-15` (`"schema_version": {"enum": [1, 2]}`, `"additionalProperties": false`, no `checks`/`inspection_complete` properties)
- **Defect:** Confirmed by direct inspection — the checked-in JSON Schema only allows `schema_version` 1 or 2 and forbids any properties beyond the ones it lists. The engine (`preflightengine.cpp:1601-1626`, `toJson`) always emits `schema_version: 3` plus a `checks` array, and the plugin's own sidecar validator (`preflightsidecarutils.h:511-537`) requires `inspection_complete` for v≥3. Every report the engine currently produces — and every fixture under `frisket-preflight/testdata/snapshots/*.json` — fails validation against the published `report.schema.json`.
- **Impact:** Violates the project's own rule ("do not invent alternate report shapes in the Qt plugin") — here the schema file itself is stale relative to the engine, so any external tool or CI step that validates against `report.schema.json` rejects all current output.

### 5. Dangling raw pointer into preflight fixup list held across a modal dialog

- **File:** `Pdf4QtEditorPlugins/FrisketPreflightPlugin/frisketpreflightplugin.cpp:707-716`
- **Defect:** `onApplyBleedFixupRequested` takes `const PreflightFixupEntry* addBleedFixup = m_reportDockWidget->addBleedFixup();` — a raw pointer into `PreflightReportModel::m_fixups`. This pointer is held across `dialog.exec()` (line 771), a modal Qt event loop that still delivers `QProcess::finished`/dock-widget updates. `PreflightReportModel::setReport()` (`preflightreportmodel.cpp:129-160`) clears and repopulates `m_fixups`; if a report reload lands while the dialog is open, the pointer is invalidated and then dereferenced at lines 714/716 after the dialog closes.
- **Failure scenario:** User opens the "apply bleed fixup" confirmation dialog, a background preflight re-run completes and refreshes the report while the dialog is still open, user confirms — use-after-free.

## Medium

### 6. Independent `expand*` box flags can produce a non-conformant PDF with bleed artwork clipped outside the visible page

- **File:** `Pdf4QtLibCore/sources/pdfbleedfixup.cpp:560-571, 647-667`; flags round-tripped independently through PageMaster job JSON (`Pdf4QtPageMaster/mainwindow.cpp:372-393`) and consumed in `pdfpagemasterexport.cpp:530`
- **Defect:** Nothing enforces `MediaBox ⊇ CropBox ⊇ BleedBox`. If a job sets `expandMediaBox=false` while `expandBleedBox`/`expandCropBox` stay `true`, MediaBox is left unchanged while CropBox/BleedBox expand past it (invalid per PDF spec). `PDFPageContentStreamBuilder::begin()` sizes its paint surface from the *current* (unexpanded) MediaBox, so the bleed fill is painted outside the paintable area and most viewers clip it away — while the fixup still reports the side as successfully applied (`pageReport.sidesApplied`), so the report/manifest falsely claims success.

### 7. OCR report `pass` stays `true` after a cancelled run

- **File:** `PdfTool/pdftoolocr.cpp:451-457` (loop break on cancellation) vs. `report.pass` only flipped to `false` on explicit page failures (lines 470, 513, 540, 553)
- **Defect:** Cancelling before any page failure leaves `report.pass == true` with a truncated `pages` array, even though the process exit code is `OcrCancelled` (line 584). A consumer trusting the JSON body over the process exit code will believe the run completed successfully.

### 8. OCR-skip status/reason values not present in the published schema enum

- **Files:** `PdfTool/pdftoolocr.cpp:493,498` (`reason = "empty"`, `status = "skipped_empty"`) vs. `frisket-ocr/schemas/ocr-report.schema.json:51,66` (`status` enum is `{"ocr","skipped_has_text","failed"}`, `reason` enum is `{"has_text","no_image_content"}`)
- **Defect:** A document with a blank/empty page produces a report that fails schema validation even though the tool reports `"pass": true`.

### 9. Per-check status conflates "warning-only" with "failed"

- **File:** `Pdf4QtLibCore/sources/preflightengine.cpp:1736-1738`
  ```cpp
  const bool checkFailed = result.errors.size() > errorsBefore;
  const bool checkWarned = result.warnings.size() > warningsBefore;
  status.status = (checkFailed || checkWarned) ? "failed" : "ok";
  ```
- **Defect:** A check that only produced warning/info findings is reported with `checks[].status == "failed"` and no `reason`, even though the overall `result.pass` can still be `true`. Downstream CI gating or UI reading `checks[]` will see "failed" for a run that actually passed.

### 10. Redaction incremental-save detector has a fixed 8 KB blind spot (false negative)

- **File:** `Pdf4QtLibCore/sources/pdfredactverifier.cpp:203-213`
  ```cpp
  const QByteArray tail = file.readAll().right(8192);
  return tail.contains("/Prev");
  ```
- **Defect:** Only the last 8192 bytes of the redacted output are inspected for `/Prev`. A redacted PDF with a large trailer/xref-stream dictionary or bulk `/ID` content between the incremental trailer and EOF can push `/Prev` past this window, so the verifier silently fails to flag that the pre-redaction revision (with sensitive content intact) is still recoverable from the file.

### 11. Bleed-fixup report can describe pages that were never actually committed

- **File:** `Pdf4QtLibCore/sources/pdfbleedfixup.cpp:509-526` (per-page report entries appended inside the loop) vs. an error on a later page returning immediately, before the whole-document commit at the end of `apply()`
- **Defect:** The document mutation is atomic and correctly rolled back on error, but `*report` is not cleared on the error path — a caller inspecting the report without first checking the returned `PDFOperationResult` sees entries for earlier pages describing changes that were never committed. Current call sites happen to discard the report on failure, so not user-visible today, but it's a real API contract inconsistency.

## Low

### 12. Unvalidated profile `severity` string only fails at report-validation time, not at profile-load time

- **File:** `Pdf4QtLibCore/sources/preflightengine.cpp` (`parseProfile`, ~line 1817): `check.severity = checkObject.value("severity").toString(check.severity);`
- **Defect:** Any string is accepted at profile-load time (schema says the enum is `{"error","warning","info"}`); a typo like `"critical"` is silently accepted, then rejected later by the stricter `preflightsidecarutils.h:280-284` validator, surfacing as a generic "PdfTool returned an invalid preflight report" error instead of a clear profile-configuration error.

### 13. `--ocr-min-text-chars 0` silently disables the OCR gate for the whole document

- **File:** `Pdf4QtLibCore/sources/pdfocrpagegate.cpp:115`: `if (countNonWhitespaceCharacters(textFlow) >= settings.minTextCharacters)`
- **Defect:** With the user-settable threshold at `0`, `count >= 0` is always true, so every page — including pure image-only scans — is classified `SkipHasText` and OCR never runs.

### 14. Misleading "timed out" diagnostic when the OCR sidecar actually crashed

- **File:** `PdfTool/pdftoolocr.cpp:229-261` — when the child process dies mid-request, `waitForReadyRead` returns false immediately, the loop breaks, and the code reports "Timed out waiting for OCR sidecar response." even though the real cause is a crash, obscuring the actual failure from operators debugging a broken sidecar install.

### 15. Signed/unsigned mismatch in JBIG2 region-offset validation (fails closed; robustness only)

- **File:** `Pdf4QtLibCore/sources/pdfjbig2decoder.cpp:3707-3833` — `offsetX`/`offsetY` are read as signed `int32_t` but passed into `checkBitmapSize(const uint32_t size)`; a negative offset reinterprets as a huge unsigned value and is rejected as "maximum bitmap size exceeded" rather than validated on its own terms. Not exploitable, but well-formed JBIG2 regions using negative placement offsets can be incorrectly rejected.

## Method

Four parallel read-only reviews were run over Frisket-authored/recently-touched code (identified via `git log --name-only` over the last 40 commits, cross-referenced with `frisket-preflight/` and `frisket-ocr/`):

1. Bleed fixup & PageMaster export (`pdfbleedfixup.*`, `pdfbleedmarginprobe.*`, `pdfpagemasterexport.cpp`, `pdftooladdbleed.cpp`)
2. Preflight engine & Editor plugin (`preflightengine.cpp`, `FrisketPreflightPlugin/*`)
3. OCR pipeline, C++ and Python sidecar (`pdfocrpagegate.cpp`, `pdftoolocr.cpp`, `frisket-ocr/service/*.py`, sidecar launcher scripts)
4. Security-sensitive parsing/signing/redaction (`pdfjbig2decoder.cpp`, `pdfsignaturehandler.cpp`, `pdfredactverifier.cpp`, `pdfsentry.cpp`, `pdfdocumentsession.cpp`, `pdftoolabstractapplication.cpp`, `pdftoolattachments.cpp`, `pdftooldecrypt.cpp`)

Findings #1–#4 above (the two highest-severity classes: destructive-write-on-cancel, and the dry-run mutation) were independently re-verified by direct source inspection after the initial pass. Upstream PDF4QT code outside the Frisket-authored surface was **not** reviewed and may contain additional issues.
